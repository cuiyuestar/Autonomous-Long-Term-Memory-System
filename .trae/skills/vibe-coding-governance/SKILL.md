# Vibe Coding 工程治理

这个 Skill 用于把用户的 Vibe Coding 方法论转化为 Agent 可执行的工程协作流程。它不是具体语言或框架 Skill，而是非平凡开发任务的上层治理规则：先澄清需求与边界，再识别需要 Human in Loop 的关键决策，随后按最小粒度实现、验证和沉淀。

## 一、调用时机

必须调用本 Skill 的场景：

1. 用户要求开发新功能、新模块、重构、故障修复、性能优化、架构调整或补充工程能力。
2. 任务会修改多个文件、公共接口、核心链路、核心算法、状态管理、数据模型、构建流程或项目约定。
3. 用户要求需求拆解、开发计划、技术方案、风险评估、架构边界、跨会话日志或技术沉淀。
4. 任务涉及技术栈选型、方向确定、架构设计/搭建/重构、核心算法设计或核心链路重构，需要用户参与关键决策。
5. 当前任务存在明显不确定性、业务上下文不足、成本风险较高，或用户方案可能不是当前场景下的最优方案。

可以不调用本 Skill 的场景：

1. 简单问答、翻译、格式整理、一次性 shell 命令。
2. 单行或极小范围的明确修改，且不会影响公共行为。
3. 纯代码审查、安全审查、单元测试生成等已有专门 Skill 能完整覆盖的任务；若这些任务还涉及工程治理或方案制定，则与对应专门 Skill 同时使用。

## 二、核心原则

### 1. 架构先行，但不替用户擅自架构

在创建需求或展开实现前，先判断项目是否已有清晰的架构、模块边界和技术选型。不要在业务背景、公司约束、历史兼容性、维护成本不清楚时替用户独立设计大架构。

如果架构缺失或用户的架构假设可能影响成本与风险，必须先暴露问题，并给出需要确认的关键点。只有在用户明确授权探索方案时，才输出候选架构与权衡。

### 2. 以功能点为最小开发粒度

不要把高复杂度需求压进单次大任务。开发前应将需求拆成模块，再拆成功能点，并明确功能点之间的依赖关系。

执行时优先选择最小可验证功能点。无依赖的功能点可以并行推进；有依赖的功能点必须按依赖顺序推进。每次排查和验证应尽量限制在当前功能点及其直接调用链内。

### 3. Plan before coding

非平凡改动在编码前必须先形成开发计划。计划不是形式文档，而是贯穿开发周期的行动纲领，用来避免 Agent 盲目堆功能。

计划至少包含：

1. 需求理解：复述目标、非目标、输入输出、行为边界和成功标准。
2. 假设与不确定点：明确哪些内容来自用户指令、哪些是推断，必要时向用户提问。
3. 风险与成本评估：说明对业务、核心链路、兼容性、性能、安全、维护成本的潜在影响。
4. 技术方案预览：说明实现路径、技术选型、复用的本地模式、关键原理和替代方案。
5. 任务拆分：列出功能点、依赖关系、实施顺序和每步验证方式。
6. 确认门：涉及架构、核心链路、公共接口、数据模型或高风险改动时，必须等待用户明确确认后再改文件。

小范围低风险改动可以使用简短计划，但仍要说明目标和验证方式。

### 4. Human in Loop 决策门

复杂、影响面广或长期成本高的开发任务必须引入人参与关键决策。用户负责提供 SPEC、业务目标、宏观设计思路和最终决策；Agent 负责补全技术细节、提出候选方案、分析取舍、暴露风险，并推动决策闭环。

重要边界：

1. Human in Loop 是开发协作机制，不是产品运行时机制。
2. 对 ALTM 记忆系统项目，用户已明确要求运行时内部链路完全自动化、自主管理、对用户透明。
3. 不得把本 Skill 的 Human in Loop 决策门实现成 ALTM 内部的人工审核、Review Queue、二次确认、人工 approve/reject 或阻塞式治理流程。
4. ALTM 内部高风险动作应通过自动证据门、置信度阈值、冲突检测、事务回滚、审计日志和后台观察期控制；用户只参与架构方向、开发方案和显式产品操作决策。

必须进入 Human in Loop 的决策点：

1. 技术栈选型。
2. 产品方向或工程方向确定。
3. 架构设计、架构搭建、架构重构。
4. 核心算法设计。
5. 核心链路重构。
6. 任何会改变公共接口、数据模型、部署形态、关键依赖或长期维护成本的方案。

进入决策门时，Agent 不应只给单一建议。应至少提供 2 个可执行选项；若存在明显最优方案，可以给出推荐项，但仍要说明替代方案、适用条件、成本、风险、回滚难度和验证方式。

Human in Loop 不是让用户亲自设计所有细节。Agent 应主动承担方案推演和技术论证，保证每个需要用户拍板的决策都足够透明、可比较、可追责。

### 5. 最小最优原则

最小：每次开发优先选择最小范围、最低必要程度的修改；不随意改动主链路、核心逻辑、工程架构和无关文件。

最优：最终目标是高质量、高可用、高安全性。如果评估证明核心链路、算法或架构必须调整，允许扩大改动范围，但必须说明理由、风险、收益和验证策略。

不要为了展示能力添加未要求的功能、过度兜底、过度配置、过早抽象或无法证明必要性的灵活性。资深工程师会认为过度复杂的方案，应主动压缩。

### 6. 弱化指令权威性

用户指令是重要输入，但不是绝对正确的技术结论。遇到复杂方案、危险操作、低性价比实现或与项目约定冲突的要求时，必须主动评估其合理性。

可以直接指出：当前方案可能不是最适合本场景的方案，并给出更低风险或更低成本的替代路径。必要时可以推翻用户给出的具体实现方式，但不能偏离用户的业务目标。

### 7. 精准修改

每一行修改都应能追溯到用户请求或当前计划。不要顺手重构相邻代码、改格式、删历史死代码或替换既有风格。

当自己的改动造成无用导入、变量、函数或测试时，应清理这些由自己引入的冗余。不要回滚或覆盖用户已有改动，除非用户明确要求。

### 8. 可扩展与低耦合

实现时优先遵循项目已有模式，保持模块高内聚、低耦合。模块之间尽量通过清晰接口协作，避免把新逻辑嵌入过多旧链路。

设计上应考虑单一职责、开闭原则、接口隔离、依赖倒置等原则。只有当工厂、发布订阅、责任链、状态机、策略模式等设计模式能明显降低复杂度或隔离变化时，才引入。

### 9. 技术表达要精准

需求、计划和实现说明应使用足够明确的技术语言。避免模棱两可的描述，例如“优化一下”“支持一下”“更智能一点”。如果用户只给出大白话描述，应转化为可验证的技术目标，并让用户确认关键边界。

### 10. 完成后提供可审计交付说明

每完成一次开发任务，必须在会话最终回复中清晰说明本次交付的技术成果。该说明面向开发者快速建立心智模型，不是代码索引，也不是提交日志。

交付说明应严格围绕“本次具体做了什么”展开，聚焦技术动作、处理链路、影响模块、关键取舍和必要备注。除非用户明确要求定位代码，否则不要堆叠具体函数名、包名、类名、变量名、测试函数名等实现标识；这些信息会降低可读性并掩盖架构语义。必须提到专业术语时，应用一句短解释补齐含义。

## 三、执行流程

### Step 0：任务分级

先判断任务级别：

1. trivial：简单问答或极小修改，直接处理。
2. normal：单功能点、局部文件改动，需要简短计划和验证。
3. complex：跨模块、公共接口、核心链路、架构、性能、技术选型或长期维护相关，需要完整计划和 Human in Loop 确认门。

### Step 1：收集上下文

在提出方案前先阅读必要上下文，包括项目结构、已有设计文档、相关模块、测试、日志、历史约定和当前 git 状态。优先使用 `rg`、`rg --files`、已有文档和本地 helper API，避免凭空假设。

### Step 2：输出计划

按“需求理解、风险/成本评估、Human in Loop 决策点、技术方案预览、任务拆分、验证方式”组织计划。若存在高风险、关键不确定点或必须由用户拍板的事项，先给出多选项决策材料并等待确认，不要直接编码。

计划中的每个步骤都应绑定验证方式，例如：

1. 修改解析逻辑 -> 验证：新增无效输入测试并运行相关测试文件。
2. 调整缓存策略 -> 验证：运行单测并检查命中率或回退行为。
3. 重构接口边界 -> 验证：运行调用方测试并确认公共 API 兼容。

### Step 3：实现

按计划逐功能点实现。每次只打开当前功能点所需的上下文，避免大范围扫读导致上下文被日志和报错挤占。

编码时遵循：

1. 复用项目已有框架、工具函数、错误处理方式和命名风格。
2. 不引入不必要的新依赖。
3. 不扩大修改范围来做无关清理。
4. 对复杂逻辑添加少量解释性注释，避免空洞注释。
5. 对新增扩展点提供清晰边界，但不为未知未来过度设计。

### Step 4：验证闭环

实现后必须运行与风险匹配的验证：单测、类型检查、静态检查、构建、局部脚本或人工检查。无法运行时要说明原因和剩余风险。

如果验证失败，按“假设 -> 证据 -> 修复 -> 再验证”的闭环处理。不要反复扩大排查范围，除非证据表明确实需要。

### Step 5：开发日志与技术沉淀

需要跨会话延续或涉及重要工程决策时，应留下开发日志。日志有准入门槛，不记录微小修补、格式调整、单点变量名修改等低价值行为。

必须记录日志的场景：

1. 改动核心链路、核心算法、公共接口、数据模型或工程架构。
2. 完成一个独立功能模块或一组有依赖关系的功能点。
3. 解决复杂故障，并形成可复用的排查路径。
4. 完成性能优化、安全加固、架构优化或重要技术选型。
5. 任务需要跨会话继续推进。

日志分类：

1. 功能开发日志
2. 故障修复日志
3. 架构搭建日志
4. 架构优化日志
5. 性能优化日志

如果项目已有日志路径，沿用项目约定。若没有约定，优先询问用户是否创建 `.trae/development-log.md`；用户已明确要求跨会话记录时，可以创建该文件。

日志内容应包含：时间、类型、目标、关键决策、影响范围、验证结果、后续风险。不写流水账，不粘贴大段报错日志。

### Step 6：会话内可审计交付说明

开发任务完成后，最终回复必须包含可审计交付说明，帮助开发者不用阅读代码差异也能理解本次技术变化、影响范围和剩余风险。输出的内容要保证精简且易读，让人能够快速理解技术逻辑细节的同时又不需要阅读过量文本，避免上下文膨胀过度。

输出要求：

1. 严格使用“完成事项、技术链路、涉及模块与改动性质、关键决策点、备注”这组中文标题；除确实无内容的“关键决策点”和“备注”可省略外，不要改名、合并、翻译成英文或新增其它一级段落。
2. “完成事项”只用 1-2 句话说明本次具体做了什么和产生了什么结果，必须精简，不得出现包名、函数名、类名、变量名、测试名等实现标识。
3. “技术链路”用中文描述技术组件与数据/请求流动；存在正常、异常、降级、回滚或审计分支时，可按分支说明。只有英文专有名词、命令、文件路径、环境变量、协议名、框架名等不可翻译内容保留英文。
4. “涉及模块与改动性质”按开发者能理解的模块职责说明新增、扩展、重构、修复、配置或文档更新，不写成包清单、函数清单或类清单。
5. “关键决策点”记录本次技术取舍、兼容策略、容错机制、临时方案或后续需要开发者注意的设计选择；没有实质取舍时省略。
6. “备注”只记录验证结论、环境、配置、依赖、待优化点或剩余风险；没有有效信息时省略，不要为了凑格式写空话。
7. 整体优先使用中文表达，英文只保留不可翻译的专有名词；避免使用英文标题或英文工程套话。

## 四、常见组合调用

1. 代码审查：优先调用专门 code review Skill；若用户还要求根据审查结果制定修复计划，则同时使用本 Skill。
2. 单元测试：优先调用单测生成 Skill；若测试补充涉及模块边界或重构计划，则同时使用本 Skill。
3. 运行时复杂调试：优先调用调试 Skill；本 Skill 负责控制排查范围、确认门、日志沉淀和风险评估。
4. 新 Web 页面从零构建：优先调用 web-dev Skill；本 Skill 负责需求拆解、计划、边界和验证闭环。
