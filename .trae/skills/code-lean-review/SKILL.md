# Code Lean Review

本 Skill 用于在代码审查中识别过度冗余、过度兜底保护和防御膨胀。它只输出审查结论和可执行建议，不直接修改代码。

## 调用时机

在以下场景触发：

1. 用户要求 code review、审查 PR/MR/diff，并关注代码质量、复杂度、维护成本或精简性。
2. 用户明确要求检查“冗余”“过度设计”“过度兜底”“防御性代码过多”“fallback 是否合理”。
3. 变更涉及核心链路、公共接口、模块边界、错误处理、fallback 策略、兼容逻辑或保护逻辑。

不替代安全审查、单元测试生成、运行时调试。若任务属于这些领域，应优先调用对应专门 Skill。

## 审查目标

重点识别三类问题：

1. 重复冗余：重复逻辑、重复类型、重复配置、重复包装层、无收益 helper、过早抽象、伪通用化。
2. 过度兜底：无证据 fallback、吞异常、catch-all、silent degrade、多层默认值、掩盖真实错误的容错。
3. 防御膨胀：重复校验、多层 guard、过度 null check、永不触发的边界保护、无明确需求的兼容逻辑。

## 上下文策略

采用分层扩大，不一开始全仓扫描：

1. 先读取用户指定 diff、文件、函数或模块。
2. 再读取同模块接口、测试、配置和直接调用链。
3. 若问题涉及职责边界或核心链路，再读取架构文档、入口层、数据模型和相关治理约定。
4. 只为证明或排除 finding 扩展上下文，避免为了找问题而扩大审查范围。

## 三证据法

正式 finding 必须同时满足三项证据：

1. 代码位置：指出具体文件、行号、函数、分支或结构。
2. 问题机制：说明冗余、兜底或防御膨胀是如何产生的。
3. 损害路径：说明它如何增加维护成本、掩盖错误、制造状态分叉、削弱可观测性或扩大行为不确定性。

缺少任一项，不得作为 finding，只能放入 Observations / Questions。

## 默认保留原则

以下兜底保护默认视为可能必要，除非有充分反证，不得轻易判为过度：

1. 外部边界：网络、数据库、RPC、文件系统、第三方服务、用户输入、环境变量。
2. 高损害操作：权限、支付、资损、数据删除、迁移、写入、跨租户隔离、安全校验。

必要但不显然的保护，可以建议补充注释、测试或监控证据，而不是直接建议删除。

## 严重度

- High：掩盖真实错误、造成双重事实源、破坏核心链路可观测性、让错误数据继续传播，或显著提高长期维护风险。
- Medium：局部重复明显、抽象边界不清、保护逻辑多层堆叠，已增加理解和修改成本。
- Low：轻微重复、可读性下降、局部 guard 或 helper 可收敛，但当前风险有限。

## 输出格式

审查报告必须 Findings 优先：

### Findings

若发现问题，按严重度排序输出：

- [High|Medium|Low] 标题
  - 位置：
  - 三项证据：
  - 为什么属于过度冗余/过度兜底/防御膨胀：
  - 风险：
  - 可执行建议：
  - 验证方式：

若没有满足三证据法的问题，明确写：未发现有充分证据支持的过度冗余或过度兜底 finding。

### Observations / Questions

用于记录证据不足但值得确认的疑点。必须明确说明“不构成 finding”，并指出缺失哪类证据。

## 自约束

1. 不为了追求简洁而建议删除正确性、安全性、可观测性或外部边界保护。
2. 不把“代码较长”直接等同于“冗余”。
3. 不把“存在 fallback”直接等同于“过度兜底”。
4. 不输出没有代码证据和损害路径的结论。
5. 对核心链路或高损害路径保持保守，必要时升级为用户决策项。
