# 发现的问题

审查日期：2026-06-30

审查范围：ALTM 当前工程代码，重点检查重复冗余、过度兜底、防御膨胀和可维护性风险。

## Findings

### 1. L2 双写冗余已经形成一致性风险

严重度：High

位置：

- `src/altm/storage/sqlite_store.py:484-526`
- `src/altm/storage/sqlite_store.py:559-592`
- `src/altm/review/queue.py:51-78`

问题机制：

L2 同时写入 `memory_units.metadata_json.review_status` 和 9 张 L2 typed table 的 `review_status`。`put_l2_atom()` 先通过 `put_memory_unit()` 独立提交 MemoryUnit，再写 typed table；`update_l2_review_status()` 先更新 metadata，再尝试更新 typed table，且没有检查 typed table `UPDATE` 是否命中行。

损害路径：

一旦 typed table 写入失败、typed row 缺失，或 `atom_type` 异常，审查链路仍可能返回成功并写审计事件，导致召回看到一套状态，结构化 L2 查询看到另一套状态。

建议：

将 L2 MemoryUnit、evidence refs、typed table 写入合并到同一个 SQLite transaction；`update_l2_review_status()` 必须校验 `atom_type` 和 `rowcount`，缺失 typed row 时显式失败或记录可审计的 degraded 状态。

### 2. CLI 与 MCP 入口存在明显重复编排

严重度：Medium

位置：

- `src/altm/cli.py:388-570`
- `src/altm/cli.py:627-766`
- `src/altm/adapters/mcp/server.py:107-340`
- `src/altm/adapters/mcp/server.py:421-505`

问题机制：

store 初始化、layer/status 解析、retriever/active-window/fusion 构造、review 操作编排在 CLI 和 MCP 中各写一遍。

损害路径：

后续新增策略参数或过滤条件时，需要同步改两套入口，容易出现 CLI 行为和 MCP 行为漂移。

建议：

抽一层应用服务，例如 `MemoryApplicationService` 或一组 `use_cases` 函数；CLI/MCP 只负责参数解析和输出格式。

### 3. TypeScript contracts 手写镜像已经滞后

严重度：Medium

位置：

- `src/altm/contracts.py:82-106`
- `src/altm/contracts.py:229-390`
- `adapters/typescript/src/contracts.ts:1-176`

问题机制：

Python Pydantic 是事实源，但 TypeScript 手写类型只覆盖到早期 contract，缺少 ReviewAction、ReviewEvent、ReviewAudit、EmbeddingConfig、ActiveWindow、ContextFusion 等 Phase 6/7 类型。

损害路径：

未来 Node adapter 会基于过期类型开发，跨语言 API 漂移不可见。

建议：

从 Pydantic JSON Schema 生成 TypeScript 类型；或者明确标注 TS adapter 当前只覆盖 Phase 1-4，并加 drift check。

### 4. 远程 embedding 故障被静默降级为普通无结果

严重度：Medium

位置：

- `src/altm/retrieval/fts.py:30-40`
- `src/altm/llm/embeddings.py:35-42`

问题机制：

远程向量请求失败后直接 `remote_matches = []`，后续 local vector / FTS / LIKE fallback 正常返回。

损害路径：

语义召回坏掉时，CLI/MCP 仍返回词面结果，调用方无法区分“远程向量无命中”和“远程向量不可用”。

建议：

保留 fallback，但在 recall metadata 或候选 explanation 中暴露 `degraded_channels=["remote_vector"]`；验证类命令可提供 strict 模式。

### 5. evidence refs upsert 语义不一致，可能留下陈旧证据链

严重度：Low

位置：

- `src/altm/storage/sqlite_store.py:185-186`
- `src/altm/storage/sqlite_store.py:891-923`

问题机制：

`put_memory_unit()` 只有在 `memory.evidence_refs` 非空时才替换 evidence table；空列表不会清理旧 refs。

损害路径：

调用者以为写入了“无 evidence refs”的 MemoryUnit，实际旧证据链仍存在，影响证据质量评分和下钻可信度。

建议：

默认总是 replace；如果确实需要“不触碰 evidence refs”，拆成显式方法。

## 总体判断

当前冗余程度为中等偏高，主要集中在 SQLite store 职责过重、CLI/MCP 双入口重复编排、跨语言 contract 手写镜像。

当前过度兜底程度为中等。大多数 fallback 位于外部边界，保留合理；主要问题是部分 fallback 缺少可观测信号。
